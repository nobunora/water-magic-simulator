# 保存済み結果の累積流出エネルギー集計実験（2026-10-04）

`scripts/benchmark_outflow_energy.py` で、保存済み0.5 m解析結果を1時刻ずつ読む。2×2セルを1 m区画とし、区画境界を通る外向き流量Qと、その運動エネルギー流率Pを計算する。区画内の0.5 mセル同士の流れは加算しない。

各面の速度は隣接するセル中心のu/vの平均、水深は上流側を用いる。Q=水深×外向き法線速度×面幅 [m³/s]、P=½×1000×Q×(u²+v²) [J/s]。保存された時刻間の台形積分で区間の流出体積 [m³] とエネルギー [J] を求める。毎時刻の区間集計を非圧縮NPZへ保存し、flush/fsyncする。最後に全NPZを1つずつ読み、総量と上位10区画を保存する。全時刻のh/u/v配列をメモリに保持しない。

## 中間ファイルを使わないメモリ集計

`python -m scripts.benchmark_outflow_energy --storage memory --run-id <解析ID>` で選択する。総合計バッファ（累積体積・エネルギーの2面）と作業バッファ（前時刻の流量・エネルギー流率、区間積分の計4面）を再利用する。作業バッファは画面表示や中間保存をしない。200×200の1 m区画ではfloat64で合計1,920,000 bytes。別途、1時刻の入力h/u/vと面流量計算の一時配列・マスクが必要で、この値はプロセス全体のメモリ使用量ではない。

## 結果画面へのメモリ方式の組込み

`floodsim/results/outflow_energy.py` に検証済みの面流量・台形積分を共通化し、実験スクリプトも同じ関数を使用する。総合計と作業用の2バッファで1時刻ずつ処理し、中間NPZは作らない。終了時に上位10件だけをJSON保存する。クリック地点の比較にも使うため、APIは全1 m区画の合計バッファをメモリに残し、作業バッファと入力フレームを解放する。ソース識別情報・解析範囲・測定時刻が同じジョブを同一プロセスで再利用する。サーバー再起動後やジョブ破棄後は、全区画のメモリを再構築するため一度集計する。

POST `/api/v1/runs/{run_id}/result-energy` が集計を開始し、GET同URLで状態・処理済み時刻数・進捗率・結果を取得する。同じ仕事は重複起動せず、集計ワーカーは1つ。保持するジョブは最大16件で、完了した古いジョブから除外する。失敗時はエラーを表示し、再実行できる。保存済みregular結果の0.5 m/1 mが対象で、1 mを等分できない格子は対応外としてエラーを表示する。

「最高総エネルギー箇所」ボタンはエネルギー上位10地点を巡回し、累積値の集計終了時刻へ移動する。計算中は `エネルギー集計中 74%（165 / 221時刻）` のように実処理数から表示する。保存終了までは最大99%、完了後に100%とする。300 ms間隔で進捗を取得し、画面を離れる際に取得を中止する。エネルギー地点の比較は累積エネルギーから換算し、累積流出量[m³]と総エネルギー[J]を表示する。既存の水深・流速順位ボタンの比較は従来の瞬間的なセル内エネルギーのまま。

実データ9f189e22でChrome操作により0%→74%→100%、順位1→10→1、最終測定時刻44秒への移動を確認。1位は累積流出84.35 m³・総エネルギー2,003,942.41 J・プリウス換算192.6 km/h。実験の上位10区画と順位は完全一致し、エネルギー差は最大6.99×10⁻¹⁰ J（実装では隣接する保存時刻の差を直接求め、実験では浮動小数の経過時間を差し引くための丸め差）。2バッファ合計は1,920,000 bytes。

証跡: `artifacts/energy-stream-benchmark/energy-production-dom.txt`、`energy-production-response.json`、`energy-production.png`。一時確認HTMLは本番へ含めない。Ruff・mypy・TypeScript、Python25件（集計/順位14件と既存の地点/表示経路11件）、画面/換算31件、OpenAPI一致、本番ビルドが成功。Import Linter・deptry・tyは環境に未導入のため実行できず、依存追加は行っていない。既存の依存ライブラリ非推奨警告とビルドの大きいチャンクの警告は残る。

### 高エネルギーの新幹線換算

プリウス換算が120 km/hを超える場合は新幹線1車両へ換算対象を切り替える。120 km/hちょうどはプリウス、30 km/h未満は従来通り力士。新幹線の表示速度は同じ総エネルギーから `sqrt(2E / 44000) × 3.6` で再計算する。44,000 kgは比較用代表値で、[JR東海のN700S確認試験車資料](https://jr-central.co.jp/news/release/_pdf/000030998.pdf)の16両で700 t以下という編成重量上限から、700/16=43.75 tを44 tへ丸めて設定した値。特定号車の実測質量ではない。瞬間エネルギー・累積エネルギー双方に適用し、速度を時速で表示する。

### ランキング外のクリック地点の比較

地図のクリックでも累積流出量・総エネルギー・換算速度を表示する。初めてクリックするとメモリ集計を開始して％を表示し、完了後はGET `/api/v1/runs/{run_id}/result-energy/point?lon=...&lat=...` で該当1 m区画だけを取り出す。途中ファイルは作らず、完成した合計配列を最大16ジョブまで保持し、ジョブ破棄時に合計も解放する。200×200区画の合計は640,000 bytes、計算中は作業用と合わせて1,920,000 bytes（入力フレームや一時配列は別）。

総エネルギーが正の区画は全区画中の順位も表示する。同じ値は区画インデックスの順とし、上位10件と同じ順位になる。流出ゼロの有効区画は静止換算を表示し、順位は付けない。全サブセルが非解析の区画はデータなしとする。クリックしたネイティブセルが非解析なら、既存の地点照会に従って比較を表示しない。範囲外は404、未集計は409。大きな配列をJSON応答へ含めない。

比較は最終保存時刻までの累積値であり、比較欄へ積算終了時刻を明記する。時刻スライダーによる水深・流速の変更では累積エネルギーを再取得しない。順位ボタンの既存比較動作は維持する。クリックの変更や画面を離れた際は前の取得を中止し、別地点の古い結果を表示しない。

実データ9f189e22の地図クリックで第1824位、累積流出14.49 m³、総エネルギー23,372.71 J、力士換算17.65 m/s・100 m走5.7秒、積算終了44秒をChromeで確認した。集計済みの地点エネルギーAPIは3回測定で0.006〜0.042秒（画面全体の描画時間ではない）。証跡は `artifacts/energy-stream-benchmark/point-energy-dom.txt`、`point-energy-response.json`、`point-energy.png`。Python16件、画面/換算36件、Ruff・mypy・TypeScriptを確認。

## 推定の限界（共通）

セル中心の保存速度から面速度を再構成する近似であり、内部計算の面流量を直接積算した値ではない。時間精度は保存時刻の間隔であり、内部の最大0.01秒刻みを再現しない。解析外周の外側に隣接セルがない面は対象外。循環して同じ区画から再び流出する水は再度計上するため、累積流出体積は初期水量を超えうる。

## 結果画面

地点の「現在水深」「流速」を2列で表示する。水深と流速は小数2桁で、流速は選択時刻の同じネイティブセルのu/vから求める。新たな読込は選択した1地点・1時刻の速度成分だけ。流速を持たない旧形式は「—」を表示する。浸水深と流速の凡例も流れ表示時に2列にする。ベクトル間隔の選択欄は削除し、既存のズームによる密度調整を維持する。

解析済み9f189e22を実際のResultPanelで表示し、測定時刻6秒で水深0.72 m・流速11.03 m/sの横並びをブラウザ確認した。元の水深・速度ランキングやSFINCS出力はそのまま。確認用HTMLは本番へ含めず、`artifacts/energy-stream-benchmark/result-layout-review.html` に再現用として保存する。
